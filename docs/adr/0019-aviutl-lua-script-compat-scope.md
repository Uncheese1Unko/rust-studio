# ADR-0019: AviUtl 拡張互換の範囲は「ExEdit Lua スクリプトエフェクト互換に絞る（方式 A）」を推奨する

- ステータス: 提案（未採用）
- 日付: 2026-11-23
- 決定者: 未決定（ユーザーの設計判断待ち）。提案者: エージェント（Issue #79 の調査）
- 関連: ADR-0006（設計判断は人間）、ADR-0014（トランジションの表現と CPU 合成経路）、ADR-0015（mp4 書き出し経路）、ADR-0017（別プロセス連携の前例）

## 背景

EPIC #78 [M4] のゴールとして、動画編集に (1) Lua スクリプトによる拡張と
(2) AviUtl の拡張機能を入れられるようにしたい（ユーザーの要望、2026-11-23）。
「AviUtl の拡張」は一枚岩ではなく、形態ごとに互換の可否と工数がまったく違う。
約束できる範囲を先に確定しないと後続（#80 基盤、#81 適用、#83 取り込み）が
手戻りになるため、本 ADR は調査（Issue #79）の結論として互換範囲の方式を
提案する。調査の詳細と証拠は試験レポート issue-0079 にある。

### 調査で確定した事実（要約）

- **バイナリプラグイン**（.auf フィルタ／.aui 入力／.auo 出力／.auc 色変換／
  .aul 言語拡張リソース）はすべて「.dll をリネームしただけ」の **x86 PE**
  である。AviUtl 本体は IA-32 アプリケーション。プラグイン SDK の ABI は
  `__stdcall` エクスポート（例: `GetFilterTable`、`GetInputPluginTable`）が
  返す関数ポインタテーブルで、構造体には `HWND`／`HINSTANCE`／
  `BITMAPINFOHEADER*` 等の Win32 型が埋め込まれ、フィルタプラグインは
  設定ウィンドウと `WM_FILTER_*`（WM_USER+100〜）のウィンドウメッセージで
  ホストと結線する。フレームは内部形式 `PIXEL_YC`（Y: 0〜4096、Cb/Cr:
  -2048〜2048）で受け渡され、ホスト側コールバック表（EXFUNC）には
  フィルタリングキャッシュや編集ファイル状態（不透明な `editp`）への
  依存がある。つまり互換には「PE ローダ」ではなく「AviUtl ホストそのものの
  再現」が要り、Linux/Rust ネイティブでは成立しない。
- **拡張編集（ExEdit）はそれ自体がフィルタプラグイン（exedit.auf）** で、
  Lua スクリプト機構は ExEdit のオブジェクト描画パイプライン内部の機能
  であって、公開されたホスト API ではない。したがってスクリプト互換は
  「ExEdit のスクリプト仕様（付属文書 lua.txt）を本アプリ側で再実装する」
  形でのみ成立する。
- **ExEdit Lua スクリプト**は Lua 5.1.4（0.93 系は LuaJIT 2.0.5 も併用）の
  バイト文字列前提で、ファイルは **Shift_JIS＋CRLF**、1スクリプト約32KB
  まで、`@名前` で1ファイルに複数登録、script フォルダ配置。API は
  `obj.*`（状態変数、load/draw/drawpoly/effect/copybuffer/getpixel/
  putpixel/getpixeldata 等）とパラメータ指令（`--track0..3`、`--check0`、
  `--dialog:`、`--color:`、`--file:`、`--param:`）からなる。
- 実在の配布スクリプト集合（sigma-axis 氏のスクリプト集＋共有ライブラリ、
  GitHub で現行メンテナンスされているもの）の実測では、使用 API は
  `obj.setoption`／`copybuffer`／`effect`／`draw`／`drawpoly`／`getpixel`
  に集中し、パラメータ指令はほぼ全スクリプトが使う。一方でピクセル処理の
  高速化に **LuaJIT FFI と `obj.getpixeldata` の生ポインタ**へ依存する
  スクリプトもあり、これは互換の深さの上限を決める。
- 本アプリ側の差し込み点は既にある。プレビューも書き出しも最終的には
  CPU 側の RGBA バッファ（`image` クレート）を通る（トランジションの
  CPU ブレンド ADR-0014、切り抜き合成、書き出しフレーム生成 ADR-0015）。
  不足する基盤は、CPU 側のテキスト描画（現行タイトルは nannou の
  `draw.text` で GUI 側のみ。フォントエンジン未導入）、図形ラスタライズ、
  `drawpoly` 相当の四角形アフィン／射影変換、`obj.effect` が呼ぶ
  **名前付き組み込み効果の再実装**、Clip へのスクリプト参照と
  パラメータ値の保持（現行は組み込みフィールドの固定集合のみ）。

## 決定（提案）

**方式 A：互換範囲を ExEdit Lua スクリプトエフェクトに絞り、本アプリの
CPU 合成経路にスクリプト実行段を新設する。バイナリプラグイン互換は
行わない。**

提案する互換範囲の具体像（採用時に #80・#81・#83 の前提になる）:

- ランタイムは **Lua 5.1 系**（mlua＋vendored を試作で実証済み。
  ExEdit の lua51.dll が Lua 5.1.4 のため意味論の基準は 5.1）。
  LuaJIT と FFI 前提のスクリプトは初期範囲の対象外とする。
- スクリプト種別は **.anm（アニメーション効果）を最初**の対象とし、
  **.obj（カスタムオブジェクト）** を続ける。.scn はトランジション
  （ADR-0014 の隣接境界モデル）への対応付けが別途要るため次段、
  .cam（カメラモデルが本アプリに無い）と .tra（トラックバー自動化の
  モデルが無い）は対象外を提案する。
- API は段階制にする。第1段：`obj` 状態変数（ox/oy/oz、rx/ry/rz、
  cx/cy/cz、zoom、alpha、aspect、time、frame、totalframe、totaltime、
  w、h）、パラメータ指令（`--track0..3`、`--check0`、`--dialog:`、
  `--color:`、`--file:`、`--param:`）、`obj.load`（figure／text／image／
  movie／framebuffer／tempbuffer）、`obj.draw`／`drawpoly`、
  `obj.setfont`、`obj.copybuffer`、`obj.setoption`／`getoption` の
  部分集合（blend、drawtarget 等）、`obj.getpixel`／`putpixel`／
  `copypixel`、`obj.rand`、`RGB`／`HSV`。第2段：`obj.getpixeldata`／
  `putpixeldata`（RGBA バッファの受け渡し）、`obj.filter`、
  `obj.getvalue`、`obj.getaudio`。
- `obj.effect` は **本アプリが再実装した名前付き効果の集合**に対して
  だけ動くものとし、初期集合の範囲は #83 の設計時に決める。未知の
  効果名・未実装 API は、無言で無視せず **明示的なエラーとして記録・
  表示する**（#72 のプラグイン不在時の扱いと同じ原則）。
- 文字コードはファイル読み込み時に Shift_JIS を前提とし、Lua 文字列は
  バイト列として扱う（試作で SJIS バイト列の効果名がそのまま届くことを
  実証済み）。UI 表示用に名前は UTF-8 へ変換する。
- スクリプトの差し込み点はクリップ単位のエフェクト段とする。
  プレビュー（320×180／10fps のフレーム選択後、テクスチャ化前）と
  書き出し（`export_frame_at` のフレーム生成）の両経路で同じ規則に
  する（プレビューと書き出しの規則一致は ADR-0015 の既存原則）。

## 検討した選択肢

| 選択肢 | 互換範囲 | 工数目安 | リスク |
|---|---|---|---|
| **A: Lua スクリプトエフェクト互換に絞る（推奨）** | .anm／.obj を中心に、FFI・外部 DLL 依存を除く配布スクリプトの相当部分。バイナリプラグインは対象外 | #80 基盤＋#81 適用＋#83 取り込み＋効果名の初期再実装で **4〜6 PBI** | 中。純 Lua のピクセル処理は書き出し解像度では重くなりうる（ExEdit 自身も lua.txt で重さを警告）。効果名の再実装範囲が互換率を左右する。SJIS・名前対応の境界ケース |
| B: 独自 Lua API ＋ AviUtl 形式の読み替え層 | A と同じ範囲に到達するのが目標だが、読み替えでカバーできる範囲次第 | A に **＋2〜3 PBI**（独自 API の設計・文書化と二重維持） | 中〜高。読み替え層の未カバー部分は「静かな非互換」になりやすい。独自 API の利用者は最初ゼロで、互換が目的なら遠回り。ExEdit の癖（例: `obj.getvalue` の zoom は 100=等倍、`obj.zoom` は 1.0=等倍）まで読み替える必要がある |
| C: バイナリ互換を Windows/Wine ブリッジプロセスで試みる | .auf フィルタの一部（ExEdit 内部に依存しないもの）。ExEdit 自体（exedit.auf）は編集ソフトそのものでホスト再現の対象外。.aui／.auo は本アプリでは ffmpeg 経路と重複 | **独立した EPIC 級（8 PBI 以上）**＋継続的な互換検証コスト | 高。Wine の問題ではなく「AviUtl ホストの再現度」の問題：EXFUNC 約50項目（フィルタリングキャッシュ、編集状態の意味論）、WM_FILTER メッセージループ、設定ウィンドウのホスティング、32bit Wine プレフィックス管理、フレーム転送（PIXEL_YC 変換）。動く／動かないがプラグインごとに変わり、約束できる範囲を事前に言えない |
| D: AviUtl 互換を捨て、独自 Lua API のみ | AviUtl の資産は使えない。新規スクリプト専用 | **約3 PBI**（#80＋#81 の互換層なし版） | 低（技術）。ただしユーザーの要望（2）「AviUtl の拡張機能が入れられる」を満たさない。A の下位互換として後から独自 API を足すことは可能 |

## 残る判断点（ユーザーの決定が必要）

1. 方式の選択（A 推奨／B／C／D）。
2. A の場合：スクリプト種別の初期範囲。.anm から始め .obj を続ける
   想定でよいか。.scn／.cam／.tra を当面対象外としてよいか。
3. LuaJIT／FFI 前提のスクリプト（`ffi.*` と生ポインタでピクセル処理
   するもの）を対象外としてよいか（推奨：初期は対象外。
   `getpixeldata` のバッファ受け渡しまでを上限とする）。
4. `obj.effect` の組み込み効果名の初期再実装セットの範囲は、#83 の
   設計時に詰める前提でよいか。
5. AviUtl2 世代の拡張（.auf2／.aui2／.auo2／.anm2 等、64bit・別 SDK・
   別仕様）は本 M4 の対象外としてよいか。

## 結果（採用された場合）

- 楽になること: 約束できる互換範囲が「ExEdit Lua スクリプトのうち
  FFI／外部 DLL 非依存のもの」と明確になり、#80（基盤）→#81（適用）
  →#83（取り込み）の順で実装が進められる。差し込み点は既存の CPU
  合成経路に乗り、新しい描画基盤はテキスト・図形のラスタライズと
  効果名の再実装に限定される。
- 制約: バイナリプラグイン（.auf 等）は永続的に対象外になる。
  `obj.effect` の互換率は再実装した効果名の範囲で決まる。ピクセル系
  スクリプトの性能は書き出し解像度で頭打ちになりうる（プレビューは
  320×180 のため問題になりにくい）。
- 覆す条件: 配布スクリプトの実態調査で FFI／DLL 依存の比率が想定より
  ずっと高いことが判明した場合は、LuaJIT 対応（mlua の luajit 機能と
  FFI 相当の受け渡し）を追加する再提案を行う。.auf バイナリ互換の
  要望が強くなった場合は、C を独立 EPIC として再提案する（本 ADR の
  範囲では扱わない）。
