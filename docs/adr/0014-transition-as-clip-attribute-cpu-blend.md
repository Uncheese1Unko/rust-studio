# ADR-0014: トランジションは後続クリップの属性として持ち、合成は CPU ブレンド＋既存テクスチャ経路で行う

- ステータス: 採用
- 日付: 2026-11-22
- 決定者: エージェント（Issue #48 の調査結論。技術方式の選定として確定する。覆す場合は本 ADR を supersede する）
- 関連: ADR-0004（コマンド層）、ADR-0011（人物切り抜きのオフライン合成）

## 背景

動画編集でクリップ境界をクロスディゾルブでつなぎたい（Issue #48 の調査、後続の実装は #49）。決めることが2つあった。

1. トランジションをモデルのどこに持つか。現行の `Clip`（`crates/studio-core/src/model.rs`）にトランジションの表現はない。一方、音声フェードは後続／当該クリップの属性（`fade_in_ms` / `fade_out_ms`、Issue #34）として持つ前例がある。
2. プレビューで2つの映像をどう合成するか。現行プレビューは 10fps の PNG フレーム列から1フレームを選び、`wgpu::Texture::from_path` で読み込んで `draw.texture` で描く方式（`apps/video-editor/src/media.rs`、`main.rs`）。人物切り抜き（Issue #22）は、画素ごとの α 合成を CPU 側（`image` クレート）で行って合成済み PNG を作り、同じテクスチャ経路で表示する前例がある。

## 決定

### モデルの持ち方

- トランジションは**後続クリップ（境界の右側）の属性**として持つ。`Clip` に次の2フィールドを追加する（どちらも `#[serde(default)]` で旧形式 JSON と互換にする）。
  - `transition_in_kind`: 種類を表す列挙（`none` / `cross_dissolve`）。当面の種類はクロスディゾルブのみ。将来の種類追加は列挙の拡張で受ける。
  - `transition_in_ms`: 長さ（ミリ秒）。0 はトランジションなし。`kind` が `none` のときは無効値として扱う。
- 設定はコマンド層経由のみ（ADR-0004）。`SetClipTransition { clip_id, kind, duration_ms }` を想定し、検証は「0 < duration_ms <= 当該クリップの長さ」を必須とする。
- **対象範囲は同一トラックで直接隣接するクリップ境界のみ**（前のクリップの `end_ms` == 当該クリップの `start_ms`）。隙間がある、または前のクリップがない場合はプレビューでトランジションを適用しない（コマンドで隣接を必須にすると移動・分割のたびに整合を保つ必要が生じるため、隣接はプレビュー適用の条件とし、設定自体は許す）。

### 時間窓とフレーム選択

- トランジションの時間窓は**後続クリップの先頭** `[start_ms, start_ms + transition_in_ms)` とする。
- 窓内の時刻 `t` では、混ぜ具合 `α = (t - start_ms) / transition_in_ms`（直線。音声フェードの直線包絡と揃える）。
- 前クリップ側のフレームは、前クリップのソース時刻 `(t - prev.start_ms)` に対応するフレームを使う。つまり前クリップはタイムライン上の終了位置を過ぎてもソース側の続きのフレームで表示され、ソースの末尾を超えたら `FrameStore::frame_path` の既存クランプで最後のフレームに張り付く。後続クリップ側は通常どおり `(t - clip.start_ms)` のフレーム。
- タイムラインの配置（クリップの開始位置・長さ・全体の尺）は変えない。ffmpeg の xfade のように尺が縮む方式は採らない。

### 合成方式

- 合成は **CPU 側で画素ごとに α ブレンド**して1枚のフレームを作り、既存のテクスチャ経路（`wgpu::Texture::from_path` → `draw.texture`）で表示する。ブレンド式は切り抜き合成と同じ `out = prev * (1 - α) + next * α`。
- 実装場所はアプリ側メディア層（コアにメディア処理を入れない原則どおり）。合成済みフレームの置き場・キャッシュは切り抜きの composite 列と同じ流儀（フレーム列として用意し、テクスチャとして読み込む）を想定するが、生成タイミング（事前生成か描画時か）は #49 の実装で決めてよい。320×180・10fps の現行プレビューでは画素ブレンドのコストは無視できる。

### 試作による確認（Issue #48）

- 使い捨ての試作で、2フレーム（testsrc2 と色相をずらした testsrc2、320×180）を α = 0.25 / 0.5 / 0.75 でブレンドし、画素値が式どおりになることを数値で確認した（例: A=(60,0,0)、B=(0,36,0) の点で α=0.5 → (30,18,0)）。
- α = 0.5 の合成画像を `wgpu::Texture::from_path` で読み `draw.texture` で描く試作アプリを Xvfb＋lavapipe で実行し、合成画像がそのまま表示されることをスクリーンショットで確認した。証拠は `docs/test-reports/evidence/issue-0048/`。

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| **後続クリップの属性（採用）** | 音声フェード（#34）の前例と一貫。クリップの移動・分割に属性が自然に付いていく。境界エンティティの整合管理が不要 | 境界そのものへの操作（両側から見た編集）は当該クリップ経由になる |
| 境界を独立エンティティとして Track/Project に持つ | 境界単位の列挙・編集が直接できる | 移動・分割・トリムの全コマンドで境界エンティティの追随が必要になり、壊れた参照（存在しない境界）を持ちうる。M2 の範囲に対して過剰 |
| 前クリップの属性（transition_out） | 後続属性とほぼ等価 | 「入り側で指定する」一般的な編集ソフトの慣習と逆で、フェードイン側の前例（fade_in は当該クリップ）とも逆になる |
| 尺が縮む xfade 方式（クリップを重ねる） | 映像としては最も自然なディゾルブ | タイムライン配置の意味が変わり（重なり区間の扱い、全体の尺）、既存の移動・トリム・分割の前提を壊す。M2 では採らない |
| nannou で2テクスチャを α 付きで重ね描き | 合成 PNG を作らずに済む | 現行の `draw.texture` 経路にテクスチャ単位の α 指定がなく、カスタムシェーダ等の追加が要る。切り抜きの CPU 合成の前例とも外れる |
| ffmpeg の blend/xfade で事前に動画として焼く | 合成品質は ffmpeg 任せ | プレビューがフレーム PNG 列方式であることと合わない。編集のたびの再レンダリングが重い |

## 結果

- #49 はこの ADR の前提（フィールド、コマンド、時間窓、α、合成方式、対象範囲）で受け入れ条件を書ける。
- 制約: トランジションは「直接隣接」が前提で、隙間のある境界には付かない。前クリップのソースに続きがない場合は最後のフレームで張り付く（静止画フェードになる）。種類はクロスディゾルブのみ。
- 覆す条件: クリップの重なり（オーバーラップ配置）をモデルが扱うようになったら、時間窓と尺の扱いを見直す。
