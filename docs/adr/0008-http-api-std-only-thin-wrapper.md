# ADR-0008: HTTP API は std のみの薄いラッパーとして実装する

- ステータス: 採用
- 日付: 2026-11-21
- 決定者: エージェント（実装レベルの判断。ADR-0004 が決めた「HTTP/JSON API が
  コマンド実行と状態ダンプを提供する」の実装方法であり、アーキテクチャと
  プロダクトの振る舞いは変えない）
- 関連: ADR-0004、ADR-0005

## 背景

PBI #4 で HTTP/JSON API を新設するにあたり、HTTP の実装方法を選ぶ必要が
あった。意味論はすべて studio-core のコマンド層が持ち、API 側の仕事は
HTTP と JSON の変換だけである（architecture ルール：薄いラッパー）。

## 決定

- HTTP サーバーは外部フレームワークを使わず、`std::net`（TcpListener）で
  実装する。新しい依存は serde / serde_json のみ。
- クレートはライブラリ（`studio_api`：リクエスト処理と serve ループ）＋
  薄いバイナリ（`studio-api`）の構成にする。overview の未決事項
  「アプリ内蔵か独立プロセスか」は、この構成ならどちらにも転べるため
  未決のまま残す。バイナリは当面、検証と computer use テストのための
  独立プロセスとして使う。
- エンドポイントは2つに絞る。`GET /project`（状態ダンプ）と
  `POST /commands`（コマンド適用、成否を JSON で返す）。失敗するコマンドは
  400 を返し、状態を変えない（コマンド層の性質そのまま）。
- 接続は逐次処理とする。ローカルの検証・観測用 API であり、同時接続の
  性能は要件にない。

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| std のみ（採用） | 依存が増えない。変換だけの責務に処理が素直に対応する。テストが軽い | ルーティングや並行処理は自前。公開 API 化には不足 |
| Web フレームワーク（axum 等） | 並行処理・ミドルウェアが揃う | 技術選定として大きく、現段階の要件（ローカル検証）に対して過剰。tokio 等のランタイム前提が全体に波及する |

## 結果

- 実アプリへの組み込みや外部公開が必要になった時点で、本 ADR を
  supersede してフレームワーク採用を再評価する。
- MCP サーバー（PBI #5）も同じ方針（薄いラッパー、依存最小）で作る。
