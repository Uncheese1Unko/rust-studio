# ADR-0010: GUI と MCP の状態共有はプロジェクトファイル経由とする

- ステータス: 採用
- 日付: 2026-11-21
- 決定者: エージェント（実装レベルの判断として記録。ADR-0006 の範囲内）
- 関連: ADR-0004（コマンド層が単一の変更経路）, Issue #3（JSON 永続化）, Issue #11

## 背景

MCP サーバーと GUI（video-editor / daw）は、それぞれ自分のプロセス内に
Project を持つ。MCP の編集受け入れ（#11、DAW 側は #16）では「MCP で
編集した結果が GUI の表示と状態ダンプに一致する」ことが求められるため、
プロセス間で Project を共有する仕組みが要る。共有しても、状態変更は
双方ともコマンド層経由であること（ADR-0004）は崩さない。

## 決定

- 共有の媒体は **プロジェクトファイル（JSON、#3 の永続化形式）** とする。
- MCP サーバーは `--project-file <path>` 指定時にそのファイルを backing
  とし、起動時に読み込み、変更系ツールの成功たびに保存する。
- GUI は環境変数 `STUDIO_PROJECT_FILE` 指定時にそのファイルを読み、
  内容の変更を監視して自動で読み直す。GUI 自身の編集も同じファイルへ
  保存し直し、双方向に一致させる。
- 変更検出はファイル内容のハッシュで行う。読み込みに失敗した場合は
  現在の状態を保って次回に再試行する（書き込み途中の読みで壊れない）。

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| プロジェクトファイル経由（採用） | 既存の永続化（#3）をそのまま使える。プロセスが落ちても状態が残る。実装が小さい | ポーリング間隔（0.5秒）分の反映遅延がある。同時編集の競合解決は「後勝ち」で、M1 の範囲に限る割り切りが要る |
| HTTP API を共有サーバーにする | リアルタイムに近い | MCP サーバーを API クライアントに作り替える必要があり、変更が大きい。サーバープロセスの管理も増える |
| GUI に MCP クライアントを内蔵する | MCP の意味論そのままで連携できる | GUI 側にプロトコル実装が増え、DAW 側でも重複する |

## 結果

- #11 / #16 の受け入れはこの方式で満たす。将来リアルタイム共有が
  必要になったら、本 ADR を supersede して API 共有方式へ移行する。
- ファイルは「最後に保存した状態が正」であり、競合解決は持たない。
  同時編集が要件になる場合はその時点で判断する。
