# ADR-0017: Vital 連携は「ヘッドレス CLAP ホスティング（別プロセス）＋プリセット JSON 注入」とする

- ステータス: 採用
- 日付: 2026-11-22
- 決定者: ユーザー（2026-11-22 に推奨案の採用を決定）。提案者: エージェント（Issue #71 の調査）
- 採用の理由: 本アプリの再生はオフラインの `render_mix` が軸でヘッドレス方式と相性が良いこと、Rust の CLAP ホスト基盤（clack-host）が最も成熟しロードを試作で実証済みであること、別プロセス分離により GPLv3 の結合解釈とプラグインのクラッシュから本体を切り離せること。判断点3点（方式 (b)＋別プロセス＋CLAP の採用、#72 で GUI 編集を対象外とすること、Vital 本体は同梱せず利用者側で入手すること）はすべて推奨どおりで確定した。
- 関連: ADR-0016（楽器モデルの Plugin バリアントが拡張点）、ADR-0009（ピッチシフト方式。プラグイン再生は別経路）

## 背景

EPIC #66 [M3] のゴールとして、DAW のノート列を外部シンセ Vital の音色で
鳴らしたい（#71 の調査）。Vital は Matt Tytel 作のウェーブテーブルシンセで、
GPLv3 のオープンソース（GitHub 公開は公式ビルドより遅れる）として
VST/VST3/AU/LV2/CLAP＋スタンドアロンで配布され、Linux 版もある
（Ubuntu 18.04 以降、GUI には OpenGL 3 が必要）。本アプリは Rust/nannou 製で、
プラグインホスティングの前例が無い。方式によって可否・工数・ライセンスの
扱いが大きく変わるため、実装（#72）の前に方式を確定する必要がある。
調査の詳細と証拠は試験レポート issue-0071 にある。

前提: 本アプリの再生は `render_mix` によるオフラインレンダリング
（再生も書き出しも同じ経路、#68）。リアルタイム音声スレッドは持たない。

## 決定

**方式 (b) ヘッドレスホスティングを、CLAP 形式＋別プロセスで実装する。**

- ホスト基盤は Rust の `clack-host`（CLAP ホスト用クレート。ロードまでの
動作を試作で確認済み）。プラグインは **ヘルパープロセス**として分離し、
本体とは IPC でノート列・プリセット・レンダリング条件を渡して
WAV 相当の PCM を受け取る。
- プリセットは.vital ファイル（JSON）を読み、プラグインのステートとして
注入する。プロジェクトにはプリセットのパス（と将来は JSON 自体の
埋め込み）を `Instrument::Plugin` バリアント（ADR-0016 の拡張点）に持つ。
- GUI 編集は #72 の範囲外とする。音作りはスタンドアロン Vital で行い、
保存した.vital を本アプリが参照する。アプリ内 GUI 埋め込み（方式 (a)）は
将来の別 PBI として切り分ける。
- Vital のバイナリは本アプリに同梱・配布しない。利用者が公式配布を
インストールし、本アプリはそれを発見して使う形にする。

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| **(b) ヘッドレス CLAP ホスティング（別プロセス）** | オフラインレンダリング中心の本アプリと相性が良い。clack-host は Rust の CLAP ホストとして最も成熟し、ロードを試作で実証済み。別プロセス分離で GPL の結合問題とプラグインのクラッシュから本体を切り離せる。GUI 埋め込みの難所（X11 親子ウィンドウ、OpenGL）を回避できる | Vital 実バイナリでの音声処理・ステート注入は未検証（#72 スパイクが必要）。CLAP 版 Vital の入手性は公式ビルドの現行版に依存。IPC とプロセス管理の実装が要る。アプリ内で音作りはできない |
| (a) ホスティング＋GUI 埋め込み（VST3/LV2/CLAP） | 音作りまでアプリ内で完結し、体験は最も良い | 工数とリスクが最大。Rust の VST3 ホストは未成熟（plughost は macOS/Windows のみで Linux 非対応）。LV2 は rust-lv2 がホスティング非対応で、livi は WIP。CLAP の GUI 拡張でも nannou/winit とのウィンドウ・ハンドル受け渡しと OpenGL 文脈の共存が未検証の難所。インプロセス読み込みは GPL の結合解釈でも最もグレー |
| (b') エンジン直接リンク（Vita 方式） | ホスト層が不要で、ヘッドレスレンダリングの実績がある（Vita が実証） | Vital のエンジンコードをリンクするため結合著作物となり、配布形態は GPLv3 が前提になる（MIT であり続けたい本アプリと衝突）。C++（JUCE 系）ビルドと FFI の負担も大きい |
| (c) スタンドアロン Vital との外部連携（仮想 MIDI＋音声ルーティング） | 実装が最も軽く、ライセンスは完全に無関係（別プログラム同士）。Vital の GUI もそのまま使える | 本アプリに MIDI 出力の新機能が要る。音声はリアルタイムキャプチャのみで `render_mix`／書き出しに統合できない（再生のたびに実時間が必要、無音書き出し不可）。どのプリセットを使ったかはプロジェクトに残らず手作業になる。利用者のセットアップ負担が大きい |

## ライセンス（GPLv3）の含意

- Vital 本体は GPLv3。FSF の公式 FAQ（#GPLAndPlugins）の立場では、
fork/exec で呼ぶプラグインは別プログラムだが、動的リンクして関数呼び出しと
データ構造を共有するプラグインは単一プログラムを形成し、結合して配布する
なら全体に GPL が及ぶ。本アプリは MIT のため、形態ごとに扱いが変わる:
- **インプロセス読み込み（(a) と (b) のインプロセス版）**: 利用者が
インストールした Vital を実行時に読むだけなら、本アプリの配布物に
GPL コードは含まれない。ただし FSF の解釈では実行時の結合も単一
プログラムとみなされ得るため、最もグレーな形態。Vital を同梱配布
する場合は GPLv3 の義務（ソース提供等）が同梱分に発生し、結合全体の
ライセンスも問われる。同梱はしない。
- **別プロセス（本提案）**: FSF FAQ の fork/exec の整理に沿い、別
プログラムとして扱える。IPC は単純なデータ受け渡しに留める。
- **エンジン直接リンク（(b')）**: 明確に結合著作物。配布するなら
本アプリ側も GPLv3 化が前提になり、現行の MIT 方針と衝突する。
- **外部連携 (c)**: 別プログラム同士で、本アプリ側に含意なし。
- プリセットの注意: Vital のファクトリープリセットは本体とは別の
ライセンスで再配布不可（Vita プロジェクトの README に明記）。本アプリが
プリセットを同梱・再配布しないこと。利用者自身のプリセットは対象外。

## #72 の受け入れ条件の骨子（採用済み）

前提スパイク（最初に実施し、結果を #72 のレポートに残す）:
- 公式 Linux 版 Vital（CLAP）の入手と、clack-host からのロード・
インスタンス化ができる。
-.vital プリセット JSON をステートとして注入し、ノート列を渡して
オフラインで PCM が得られ、無音でないこと（周波数測定等で確認）。

本実装の条件:
- `Instrument::Plugin { format, plugin_id/path, preset_path, state_json?}`
を ADR-0016 の拡張点に実装し、`SetTrackInstrument` で設定できる。
- `render_mix` のノート再生で Plugin 楽器のトラックはヘルパープロセス
経由のレンダリング結果を使う（再生・WAV 書き出しの両方）。
- ヘルパーが無い／プラグインが見つからない／プリセットが読めない場合は
そのトラックの音はミックスに出ないが、**無言で無音にせず、明示的な
エラー状態として記録し画面に表示する**（Issue #72 の受け入れ条件
「明確なエラーを出してアプリが落ちない」に従う。全体の再生・書き出しは
止めず、他のトラックとサンプラー再生は壊さない）。
- Undo・MCP・プロジェクト保存（JSON）で楽器設定が往復する。

## 結果

- 楽になること: 実装範囲が「ロード→ステート注入→ノート送信→PCM 取得」に
限定され、GUI 埋め込みの不確実性を #72 から外せる。ライセンスの立場も
別プロセスで明確になる。サンプラー（#68）と並ぶ第2の楽器として
Plugin が増えるだけで、ノート／クリップのモデルは変わらない。
- 制約: アプリ内で Vital の音作りはできない（スタンドアロン併用）。
Vital の CLAP 版の配布状況に依存する。リアルタイム性は持たない
（本アプリの再生モデル上は問題にならない）。
- 覆す条件: 公式 Linux 版に CLAP が含まれない、またはステート注入で
プリセットが再現できないことがスパイクで判明した場合は、(b) の形式を
LV2（livi）へ差し替えるか、(c) への格下げを再提案する。
