# ADR-0024: 音声分離の実行環境 — Demucs を採用する（Spleeter は Python 3.12 では動かない）

- ステータス: 採用
- 日付: 2026-11-26（提案）／2026-11-26（ユーザーが選択肢 B を選んで採用）
- 決定者: ユーザー（2026-11-26、選択肢 B「Demucs に乗り換える」を選択）。調査と提案: エージェント（Issue #98）
- 関連: ADR-0016（ノート／音色モデル）、ADR-0017（外部ツールの別プロセス分離）、ADR-0018（音色コレクション）、ADR-0006（設計判断は人間が持つ）

## 背景

EPIC #97（WAV を分離し、各ステムをメロディと音色に分解する）の前提として、開発 VM で当初指定の Spleeter が実際に動くかを Issue #98 で実証した。VM の Python は 3.12.3 で、Spleeter／TensorFlow は未インストールだった。

調査の結論: **Spleeter はこの VM の Python 3.12 では、正規のインストールでも依存を寄せた強制構成でも動かない。** 証拠は次のとおり（詳細とログは試験レポート issue-0098）。

1. **正規インストール不可**: 最新の spleeter 2.4.2 は `requires_python: <3.12,>=3.8` を宣言し、`tensorflow==2.12.1`（対応 Python は 3.8〜3.11）と `pandas<2.0.0` を固定する。Python 3.12 の pip は 2.4.2 を解決できず spleeter 2.1.0 まで落ち、その依存する旧 numpy がソースビルドになり、`numpy.distutils`（Python 3.12 で削除）由来の `NameError: name 'CCompiler' is not defined` で失敗する。
2. **強制構成でも推論不可**: spleeter 2.4.2 を `--no-deps --ignore-requires-python` で入れ、依存を Python 3.12 対応版に寄せた構成（tensorflow 2.17.1、numpy 1.26.4、pandas 2.1.4、norbert 0.2.1 等、venv 容量 2.3GB）では、`import spleeter` とモデル（2stems）のダウンロード・展開までは成功した。しかし分離実行が `spleeter/separator.py` の `create_estimator` 内 `tf.estimator.RunConfig` で `AttributeError: module 'tensorflow' has no attribute 'estimator'` となり失敗した。`tf.estimator` は TensorFlow 2.16 で削除されている。
3. **estimator の単独提供も不可**: `tensorflow-estimator` パッケージは 2.15.0 が最終で、TF 2.17 に対しては内部 API（`tensorflow.python.distribute.estimator_training`）の削除により import 自体が失敗する。estimator を含む最後の TensorFlow 2.15 系は Python 3.12 用ホイールが存在しない（対応は 3.11 まで）。

つまり障壁は「バージョンの組み合わせ」ではなく、**Spleeter の推論経路そのものが削除済み API（tf.estimator）に依存している**ことにある。これを回避するには Spleeter 内部の推論実装を書き換える（フォーク保守）しかなく、製品に抱えるには脆すぎる。

なお、分解の後半（ピッチ追跡）は分離ツールと独立に実証できた。自己相関ベースの試作（外部クレートなし）は、既知メロディ（A4→C5→E5→A5、各 500ms）の単体レンダリングに対し **4音すべて音高一致・開始誤差 14ms 以内** で抽出できた。#100（メロディ抽出）はこの試作を土台に進める。

## 決定

**分離ツールは Demucs とする**（ユーザーが 2026-11-26 に選択肢 B を選択）。骨格は次のとおり。

- **ツールとモデル**: Demucs を別プロセスで実行する（`python -m demucs`、ADR-0017 と同じ別プロセス分離の考え方）。モデルは **htdemucs**（4ステム: vocals／drums／bass／other）、デバイスは CPU を明示する。
- **実行環境（venv）**: リポジトリ管理外の専用 venv `~/demucs-venv` に、PyTorch の **CPU ホイール**と demucs を入れる（CUDA 一式は入れない）。DAW からの解決順は次のとおりとし、どちらでも demucs を import できなければ「未導入」として明示エラーにする（黙って波形配置だけに倒したりしない）。
  1. 環境変数 `RUST_STUDIO_DEMUCS_PYTHON`（python 実行ファイルへのパス）
  2. 規約パス `~/demucs-venv/bin/python`
- **生成物の置き場**: ステム WAV はプロジェクトに紐づく生成物ディレクトリに置く。プロジェクトファイルがある場合はその同階層の `<プロジェクトファイル名（拡張子なし）>.stems/<元ファイル名>-<元パスのハッシュ>/` 配下（Demucs の出力レイアウト `htdemucs/<曲名>/<ステム>.wav` をそのまま使う）。プロジェクトファイルが無い GUI デモモードでは `media_dir()/stems/` 配下に同じ構造で置く。再実行時は同じディレクトリへ上書きする（決定的な配置）。
- **適用は原子的**: 分離・ピッチ追跡・音色登録の結果は、複製の上でコマンド列を適用してから `History::commit_replacement` で一度に差し替える（MIDI 取り込みと同じ性質。Undo 1回で分解前に戻れる）。分離が失敗したらプロジェクト状態は変えず、エラーを利用者へ見える形で返す（GUI はステータス表示、CLI は終了コード＋メッセージ）。
- **GUI の実行方式**: 分離は重い処理なのでワーカースレッドで実行し、完了を `update()` で受けてから適用する（UI を固めない）。CLI 検証入口（`--separate`）は同期実行でよい。
- **分解の最終形**（#99〜#101 の到達点）: 1ステム = 1トラック = 1クリップ。
  - 音高が抽出できたステムのクリップは**ノートクリップ**にする（`source` は空文字。モデルの運用どおり、ノートのあるクリップは波形を鳴らさない）。#99 の段階では全ステムが波形クリップで入り、#100 で音高の取れたステムからノートクリップへ置き換わる。
  - 音高の定まらないステム（ドラム等）は**波形クリップのまま**残す（無理にノートを作らない。ドラムは波形として鳴るのが正しい）。
  - 全ステムの音声を Sampler 音色として `Project.tones` に登録し、そのトラックへ `SetTrackTone` で割り当てる。`root_note` は抽出ノート列の最頻音高、ノートが空のステムでは 60（中央値的な既定）。
  - 分離前の元 WAV のトラック／クリップは従来どおり残す（分解は追加のみ）。

## 検討した選択肢

| 選択肢 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A. Python 3.11 の venv を別途用意し Spleeter を使う | uv のスタンドアロン CPython 等で 3.11 を導入し、spleeter 2.4.2 + tensorflow 2.12.1 の設計どおりの環境を作る | ユーザーが当初指定した Spleeter をそのまま使える。バージョンが設計どおりで最も確実 | VM に python3.11 が無い（apt に候補なし。uv 導入か PPA 追加が要る）。TF 2.12 系は旧く、保守されなくなる一方。venv 約2.3GB |
| **B. Demucs に乗り換える（採用）** | PyTorch 系の分離ツール demucs（`requires_python >=3.10` で 3.12 対応、torch は CPU ホイールを使う） | 現行 Python 3.12 のまま入る。分離品質は Spleeter より高いとされる。4ステム（vocals/drums/bass/other）が標準 | 当初の指定からの乗り換え。torch が大きく（CPU ホイールで約800MB級）初回モデル取得も要る。実行時間は Spleeter より重い傾向 |
| C. 外部で分離したステムの取り込みのみ対応する | 分離はユーザーが手元の環境や外部サービスで行い、DAW は「ステム WAV 群の取り込み→メロディ抽出→音色化」だけを実装する | ML 実行環境を製品が抱えずに済む。#100・#101 の価値はそのまま届く | 「WAV を読み込ませたら自動で分離」という体験にはならない。手間がユーザーに移る |
| D. Spleeter の推論経路をパッチして 3.12 で動かす | `create_estimator` を tf.estimator なしで書き換えたフォークを保守する | Spleeter の名前とモデルはそのまま | ライブラリ内部の書き換え保守が恒常化する。TF／Keras の更新のたびに壊れ得る。**非推奨** |

当初の推奨は A（指定どおりの環境で Spleeter を使うのが最も素直）だったが、ユーザーは 3.12 に残ることと分離品質を優先し、**B を選択した**（2026-11-26）。

## 結果

- EPIC #97 は Demucs 前提で再開する。#98 は「Spleeter 不可の実証＋Demucs 採用の決定」をもって完了とする。#99 のタイトル・本文は Demucs 前提に書き換えた。
- 製品は Demucs の実行環境（venv）を同梱せず、利用者側の venv を規約パス／環境変数で解決する（Vital 本体を同梱しない ADR-0017 の方針と同じ）。未導入は明示エラーとして扱う。
- Demucs の分離は CPU では重い（分のオーダーになり得る）。GUI の非同期実行とステータス表示はこの前提で設計する。所要時間の実測は #99 の試験レポートに残す。
- ピッチ追跡の試作と答え合わせ結果はそのまま #100 の土台になる。
- 覆す条件: Spleeter が tf.estimator 依存を外した新版を出し、Python 3.12 以降に対応したら、選択肢は再評価する。
