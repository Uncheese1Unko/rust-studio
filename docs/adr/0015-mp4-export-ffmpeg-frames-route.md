# ADR-0015: mp4 書き出しは「アプリ側でフレーム列と音声をレンダリングし、外部 ffmpeg でエンコードする」経路とする

- ステータス: 採用
- 日付: 2026-11-22
- 決定者: エージェント（Issue #52 の調査結論。書き出し経路という技術方式の選定として確定する。覆す場合は本 ADR を supersede する）
- 関連: ADR-0011（人物切り抜きのオフライン処理）、ADR-0014（トランジションの表現と合成、提案中）

## 背景

動画編集のタイムラインを mp4 に書き出す経路が未決定だった（Issue #52 の調査、後続の実装は #54）。現行プレビューは 320×180 / 10fps の PNG フレーム列という最小経路で、そのまま書き出すと品質が足りない。決めることは、(1) ffmpeg への入力の作り方、(2) 解像度・FPS の決め方、(3) 音声の扱い。

前提として、動画編集のメディア処理は既に外部 ffmpeg に寄せている（サンプル素材の生成、フレーム列の展開はいずれも `apps/video-editor/src/media.rs` から ffmpeg を起動）。音声ミックスの規則（クリップゲイン、トラック音量・パン、フェード）は DAW 側の `render_mix`（Issue #13・#34）が実装済みの規則として存在する。

## 決定

### 経路

- 書き出しは**アプリ側（動画編集のメディア層）がフレーム列と音声をレンダリングし、外部プロセスの ffmpeg で mp4 にエンコードする**。
  1. 出力フレームごとに、タイムラインの合成規則（後述）でフレーム画像を用意する。内部表現はプレビューと同じ PNG フレーム列でよい。
  2. 音声はタイムラインの音声トラックをミックスした WAV を用意する。
  3. `ffmpeg -framerate <fps> -i frames -i mix.wav -c:v libx264 -pix_fmt yuv420p -c:a aac -movflags +faststart` でエンコードする。書き出し先へは一時ファイル経由で rename して確定させる（プロジェクト保存のアトミック方式の前例に倣い、途中失敗で壊れた mp4 を残さない）。
- エンコードを自前実装（Rust のエンコーダ／ミキサクレート）はしない。H.264 エンコードの成熟した経路は ffmpeg の libx264 であり、プロジェクトのメディア処理が既に ffmpeg 前提であることとも一貫する。

### 解像度と FPS

- 書き出し解像度と FPS は**書き出し設定として持つパラメータ**とし、既定は **1280×720 / 30fps** とする。プレビューの定数（320×180 / 10fps、`media.rs` の `FRAME_*`）はプレビュー専用であり、書き出しには流用しない。書き出し用のフレームは素材から書き出し解像度で別途用意する。
- 素材の解像度が書き出し解像度と違う場合は、書き出し解像度にスケールして合わせる（縦横比の扱いの細部は #54 の実装で決める）。

### 合成規則（書き出し範囲）

- 全体の長さは、全トラックを通じたクリップ終端の最大値とする。
- 映像: 各出力時刻で、映像トラックのうちその時刻を覆うクリップをトラック順に合成する（プレビューの `active_video_clip` と同じ「トラック順で最初に覆うもの」を基本とし、切り抜き合成とトランジションはプレビューと同じ規則で書き出し解像度において再構成する。トランジションの規則は ADR-0014 の採用内容に従う）。
- 音声: タイムラインの**音声トラック**を、DAW の `render_mix` と同じ規則（クリップゲイン×トラック音量、パン、フェード）でミックスする。出力は**ステレオ、サンプルレート 48kHz、AAC** とする（`render_mix` の出力がステレオであることに合わせる）。映像より短い場合は無音で埋め、長い場合は全体の長さで切る。
- フレームのソース時刻は `offset_ms + (t - start_ms)` で計算する（ADR-0014 と同じ定義。現行プレビューの `source_time_ms` は offset を加えていないが、書き出しではこちらを正とする）。
- どの映像クリップにも覆われない時刻のフレームは**黒フレーム**とする（プレビューが背景色で描く区間に相当）。
- **映像ソースに埋め込まれた音声は、最初の実装では扱わない**（既知の制限として記録する）。現行メディア層には映像ファイルから音声を取り出す経路がなく、音声トラックで BGM 等を載せる運用が M1 までの前提であるため、まず音声トラックのミックスを対象とする。映像ソースの音声が必要になったら別 PBI で抽出経路ごと扱う。

### 試作による確認（Issue #52）

- 使い捨ての試作（コマンドとスクリプト）で、2クリップ（1280×720、境界に ADR-0014 の方式の1秒クロスディゾルブ）と2トラック分の音声ミックスを持つ5秒のタイムラインを、この経路で書き出した。
- 結果の mp4 を ffprobe で確認: H.264、1280×720、30fps、AAC 48kHz、長さ 5.000 秒。書き出し mp4 のトランジション中間（2.5秒）のフレームが、α=0.5 の合成フレームと画素照合で一致（符号化の誤差範囲）した。証拠は `docs/test-reports/evidence/issue-0052/`。

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| **アプリ側レンダリング＋外部 ffmpeg（採用）** | 合成規則がプレビューと同一の実装に寄せられ、見た目の一貫性を保ちやすい。ffmpeg は既存の前提。試作で実証済み | フレーム列の生成コストは全フレーム分。高速化は将来の課題（イシューのスコープ外） |
| ffmpeg のフィルタグラフ（xfade 等）にタイムラインを翻訳する | エンコードまで ffmpeg 内で完結する | 複数トラック・隙間・切り抜き・任意配置をフィルタグラフへ翻訳する規則が別途必要になり、プレビューとの二重定義になる |
| プレビューのフレーム列（320×180 / 10fps）をそのまま使う | 実装が最小 | 品質が書き出しの用途に足りない（イシューの根本原因そのもの） |
| Rust のエンコーダ／ミキサを自前で持つ | 外部プロセス依存が減る | H.264 エンコードの成熟度とライセンスの面で現実的でない。既存の ffmpeg 前提とも外れる |

## 結果

- #54 はこの ADR の前提（経路、既定 1280×720/30fps、合成規則、音声の範囲と制限）で受け入れ条件を書ける。
- 制約: 映像ソース埋め込み音声は対象外（制限として明記）。書き出し速度の最適化は扱わない。トランジションを含む書き出しは ADR-0014 の採用が前提になる（未採用の間は、トランジションなしの範囲で #54 を進められる）。
