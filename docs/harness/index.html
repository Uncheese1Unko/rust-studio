rust-studio ハーネス設計

AI駆動開発の「仕組み」と「段取り」— 動画編集ソフトと DAW を、AI が自律的に作り、人間が設計判断を握るための土台

対象リポジトリ： rust-studio（Rust + nannou、モノレポ）／ 方式の出典： ohta-rh 氏の x-modoki-v2・insta-modoki（判断ポリシーのみ本プロジェクト用に変更、ADR-0006）／ 作成： 2026-11-21

1. 全体像 — 人間・AI・リポジトリの役割分担

このハーネスの考え方は単純です。判断とルールはリポジトリに固定し、AI はその中で自律的に回り、人間は設計判断にだけ立つ。AI のコンテキストは圧縮されても、リポジトリに書いたことは正確に残るからです。

図1：三者の関係。AI は止まるべき所（設計判断）でだけ人間に渡し、それ以外はリポジトリのルールに従って回り続ける

2. ハーネスの構成要素

置き場所役割
CLAUDE.md入口。要点だけを書き、本体はルールへ参照する（薄く保つ）
.claude/rules/（8本）起票作法／デリバリーループ／TDD／コードレビュー／完了の定義／バグ対応／アーキテクチャ／文書。ハーネスの本体
.claude/agents/code-reviewer.md独立レビュアーの定義。実装者とは別の新規エージェントが、イシュー番号と diff 範囲だけで審査する
docs/adr/判断の記録（ADR）。採用済みは編集せず supersede。決定者（人間／エージェント）を明記
.github/ISSUE_TEMPLATE/EPIC／PBI のテンプレート。完了の定義チェックリスト入り
docs/test-reports/試験レポートと証拠（スクリーンショット等）。close の必須条件
docs/log.mdドキュメントの更新履歴

3. 段取り（1）— イシューの切り方

作業は EPIC → PBI の階層で管理します。EPIC は「成果」、PBI は独立に届けられる振る舞いの縦スライス。レイヤー（バックエンド部分など）では割りません。

図2：イシュー階層と起票の鉄則。実装者がイシューだけで着手できることが「手戻りゼロ」の条件

4. 段取り（2）— デリバリーループ

1イテレーション＝1 PBI を、着手から close まで運びます。EPIC の一覧の順に取り、blocked by が閉じるまで先に進みません。

図3：デリバリーループ。バグ・レビュー差し戻し・赤い CI は停止理由にならない。止まるのは判断と人間の担当分だけ

5. 品質ゲート — 「完了」の定義

常時 TDD

落ちるテストが要求していない本番コードは書かない。落ちた記録（red）を試験レポートに残す。記録がなければ TDD とは認めない。

独立コードレビュー

実装者と別の新規エージェントに、イシュー番号と diff 範囲だけを渡す。自分の要約や推論は渡さない。APPROVE が出るまで新しいレビュアーで回す。

証拠つき試験レポート

受け入れ条件ごとの結果と証拠（スクリーンショット、状態ダンプ、音声）を docs/test-reports/ に残してから close する。

バグは直し切る

見つけた時点で再現→根本原因→落ちるテスト→修正まで。severity で先送りしない、blocked にしない。設計判断が絡む場合だけ人間に渡す。

6. 判断ポリシー — ohta 方式から変えた1点

ohta 方式の原則は「ユーザーに聞かない。判断はエージェントが決めて ADR に書く」。本プロジェクトではこれを採用しません（ADR-0006）。理由は、プロジェクトの目的が「人間の設計判断を理由つきで蓄積し、改善していくこと」にあるためです。

判断の種類扱い
設計判断（アーキテクチャ、技術選定、プロダクトの振る舞い）AI は決めない。needs-decision で止まり、人間が決める
実装レベルの小判断（命名の細部など）AI が決めてよい。ADR に記録し（決定者：エージェント）、最終報告で明示する

7. AIネイティブ設計との接続

ハーネスが回す対象（アプリ側）も、AI が触れる形に設計されています。状態変更は共通コア studio-core のコマンド層経由のみ（単一の変更経路）。GUI・HTTP API・MCP サーバーはすべて同じコマンドを実行し、状態は JSON で全量ダンプできるため、画面で起きたことが API でも観測できます（computer use テストの前提、ADR-0004／0005）。
