## 前提（#30 調査の結論と読み替え）

- ドロップイベントから座標は取得できない（パスだけが届く）。
  そのため受け入れ条件1の「ドロップ位置」は、#30 が申し送った
  代替規則「選択中トラック＋再生ヘッド位置」で読み替えた。
  さらに動画編集には映像／音声の2種のトラックがあり、文字どおり
  選択中トラックへ置くと種別不一致のクリップ（音声トラック上の
  動画など）が生じてプレビュー対象外になるため、配置先を
  「素材種別に合うトラック（選択中を優先、合わなければその種別
  の先頭トラック）＋再生ヘッド位置」に広げた。DAW #42（単一種別）
  との差はこの点のみで、レビューでも妥当と判断された。
- 対応拡張子は media.rs の利用対象: 動画 mp4/mov、画像 png/jpg、
  音声 wav。長さは動画・音声は ffprobe の実尺（取れなければ
  2,000ms）、画像は 2,000ms。source にはドロップされた絶対パス
  を記録し、media.rs の resolve_source でそのまま解決できる。

## 受け入れ条件ごとの結果

### AC1: 対応形式のファイルをドロップすると、クリップが置かれプレビューに映像が出る — ✅（代替規則で）

- `event()` が `WindowEvent::DroppedFile` を受け、`handle_drop`
  が `edit::drop_placement_command` の AddClip を History 経由で
  適用し、素材展開・テクスチャ・保存まで通常配置と同じ後処理を
  行う。
- イシュー指定テスト `drop_position_maps_to_track_and_time` が
  種別振り分け・選択中優先・負ヘッドの0丸め・配置不能（合う
  トラック無し／長さ0）を固定。拡張子判定は
  `drop_kind_classifies_by_extension`。
- 実アプリ証拠（`evidence/issue-0053/`）: XDND で movie.mp4 を
  ドロップし、`drop imported: ... at 0ms`、ダンプに実尺
  duration 3000ms のクリップ、`preview: source=/tmp/drop53/
  movie.mp4 ...` の連続出力を確認。

### AC2: 対応外のファイルをドロップしても何も起きず、ログに理由が出る — ✅

- 対応外・配置不能・コマンド拒否の各経路が理由付きログを出して
  状態を変えない。実アプリで notes.txt のドロップが
  `drop rejected: ... (unsupported file type; ...)` となり、
  取り込み件数が増えていないことを確認。
- 複数ファイルは先頭1件のみ処理し、残りは `drop skipped:` と
  ログに出す（1秒以内の連続ドロップを同じバーストとみなす。
  DAW #42 と同じヒューリスティクス）。

### AC3: 置かれたクリップが通常のクリップと同じく移動・トリム・分割できる — ✅（移動は実証、トリム・分割は構造で担保）

- 生成されるのは通常の AddClip クリップで、ドロップ固有の状態
  を持たない。実アプリでドラッグ移動（start 0→500、スナップ
  込み）が保存とダンプに反映されることを確認した。トリム・
  分割は通常クリップと同一経路（分割の GUI 操作自体は #43 の
  担当範囲）。

## 証拠の限定（レビューの Minor 指摘への明記）

- 実アプリ証拠は mp4 のドロップのみ。wav/png/mov/jpg のドロップ
  と、トリム・分割の実アプリ操作は証拠に含めていない（単体
  テストと「通常クリップと同一の生成物」という構造でカバー）。
- 既知の制限: バースト判定の `last_drop_at` は拒否されたドロップ
  でも更新されるため、対応外を落とした直後1秒以内の正規ドロップ
  が2件目としてスキップされ得る（DAW #42 と同一の方式）。
