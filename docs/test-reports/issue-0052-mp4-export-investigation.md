# 調査レポート： Issue #52 mp4 書き出し経路の選定

- 日付: 2026-11-22
- 実行者: エージェント（並行レーンC、コア・調査担当）
- 種別: 調査 PBI（本体コードの変更なし。成果物は ADR と本レポート、証拠。試作は使い捨てのコマンドとスクリプト）
- 結論: **ADR-0015**「mp4 書き出しは『アプリ側でフレーム列と音声をレンダリングし、外部 ffmpeg でエンコードする』経路とする」
- 環境: Yoko の VM（Linux、ヘッドレス）。ffmpeg 8.1.2。実機のプレイヤーでの再生確認はしていない（ffprobe による仕様確認まで）。

## 受け入れ条件ごとの結果

### AC1: 書き出し経路（ffmpeg への入力の作り方、解像度・FPS の決め方、音声の扱い）が ADR として決定され、記録されている — ✅

- [ADR-0015](../adr/0015-mp4-export-ffmpeg-frames-route.md) を作成し、`docs/adr/index.md` に登録した。
- 決定の要点：
  - 入力の作り方: アプリ側（動画編集のメディア層）が、タイムラインの合成規則でフレーム列（PNG）を用意し、音声トラックをミックスした WAV を用意して、外部 ffmpeg で `libx264 + AAC, yuv420p, +faststart` にエンコードする。確定は一時ファイル経由の rename でアトミックに行う。
  - 解像度・FPS: 書き出し設定のパラメータとし、既定は **1280×720 / 30fps**。プレビューの定数（320×180 / 10fps）は流用せず、書き出し用フレームを素材から書き出し解像度で別途用意する。
  - 音声の扱い: タイムラインの音声トラックを DAW の `render_mix` と同じ規則でミックスして含める。**映像ソースに埋め込まれた音声は最初の実装では扱わない**ことを既知の制限として ADR に明記した（現行メディア層に映像からの音声抽出経路がないため）。

### AC2: 試作コマンドで短い mp4 が実際に生成され、ffprobe で長さ・解像度・コーデックが確認できている — ✅

- 試作タイムライン（使い捨てスクリプトで再現）: 映像クリップ2本（testsrc2 1280×720 を素材に、0–2秒と2–5秒。境界には ADR-0014 の方式で1秒のクロスディゾルブ）、音声2トラック相当のミックス（440Hz を音量0.8、660Hz を音量0.4で重ねた5秒 WAV）。
- 経路: フレーム列を 30fps で150枚レンダリング（トランジション窓では前クリップのソース継続フレームと α ブレンド）→ ffmpeg でミックス WAV と合わせてエンコード。
- 出力 [export.mp4](evidence/issue-0052/export.mp4) の ffprobe 結果（[ffprobe-export.txt](evidence/issue-0052/ffprobe-export.txt)）: **H.264、1280×720、30fps、AAC 48kHz、長さ 5.000 秒**、サイズ 1,468,000 バイト。
- 中身の照合: 書き出し mp4 の 2.5 秒地点（トランジション中間）のフレーム [check-mid.png](evidence/issue-0052/check-mid.png) が、α=0.5 の合成フレームと画素値で一致した（差は符号化誤差の範囲。例: (8,8) で書き出し (28,18,0) に対し合成 (30,20,0)、純粋な前クリップの同地点は (60,0,0)）。1.0 秒地点は前クリップそのものだった。

### AC3: 実装 PBI の受け入れ条件に使える形で、書き出し範囲（トラックの合成規則を含む）と検証方法が決まっている — ✅

後続の実装 PBI（#54）は、ADR-0015 を前提に次の形で受け入れ条件を書ける。

- 書き出し範囲: 全体の長さは全トラックのクリップ終端の最大値。映像はプレビューと同じ合成規則（トラック順、切り抜き、トランジションは ADR-0014 の採用内容に従う）を書き出し解像度で再構成する。音声は音声トラックのミックスのみ（映像ソースの埋め込み音声は対象外＝制限として明記済み）。
- 検証方法（#54 で使える形）:
  - ffprobe で、出力の映像コーデック（H.264）・解像度・FPS・音声コーデック（AAC）・長さ（タイムライン長と一致）を機械確認する。
  - 書き出し mp4 から切り出したフレームと、プレビュー側の合成結果を画素照合する（本調査と同じ方法が使える）。
  - 音声は、ミックス WAV の規則（ゲイン・パン・フェード）どおりの波形になっていることを、無音区間と音量で確認する。
  - 失敗時（ffmpeg 不在・素材欠落）: エラーになり、壊れた mp4 が書き出し先に残らないこと。書き出しでプロジェクト状態が変わらないこと（状態ダンプ不変）。
  - 実装上の注意: DAW 側の `render_mix` は `apps/daw` にあるため、規則の共有方法（コアへの切り出し等）は #54 の実装で決める。本調査は規則の同一性だけを前提として固定した。

## 調査の過程で分かったこと

- 動画編集のメディア処理は既に ffmpeg 前提（素材生成・フレーム展開）であり、書き出しも同じ前提に乗るのが一貫する。自前エンコーダを持つ理由はない。
- プレビューのフレーム列は素材単位で全フレームが展開されているため、トランジションの「前クリップのソース継続」も書き出し解像度で同じ考え方が使える（解像度が違うのでフレーム自体は書き出し用に別途用意する）。
