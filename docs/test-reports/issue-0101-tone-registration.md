## 設計

- 音色登録と割り当ては、分離の原子的適用（`apply_stems`）の一部として
  コマンド列で行う: ステムごとに `AddTone`（`Instrument::Sampler
  { source: ステム WAV, root_note }`）→ `SetTrackTone` でそのステムの
  トラックへ割り当てる。失敗時は取り込み全体が失敗し、プロジェクトも
  履歴も変わらない（従来どおり）。
- 音色名はトラック名と同じ `{元ファイル名} / {ステム名}`。
- **root_note の決定規則（決定的）**: 抽出ノート列の最頻音高。
  同数の場合は最初に現れた音高を採る。**ノートが空のステムでは
  既定値 60（中央の C）とする**（イシューの指定どおり、ここに明記）。
- 再生は既存の `render_mix`＋`pitch_shift`（ADR-0009）をそのまま使う。
  サンプラーは素材全体をワンショットとして鳴らす既存の意味論
  （#19／#73）であり、ステム音色でも同じである。つまり書き出しでは
  「抽出ノート列が、ステム素材を素材として、root_note 基準の
  ピッチシフトで鳴る」。ステムの自動トリミングはスコープ外
  （イシュー明記）なので、素材の冒頭から鳴る。この前提は
  受け入れ条件3の結果にもそのまま書く。

## 受け入れ条件ごとの結果

### 1. 各ステムが Sampler 音色として登録され、トラックへ割り当てられる — ✅

CLI 駆動（`daw --separate`、メロディのみのテスト WAV）の保存
プロジェクトで確認した: `tones` に4件の Sampler 音色
（source＝各ステム WAV）が登録され、各ステムトラックの
`tone_id` が対応する音色を指す。単体テスト
`apply_stems_registers_a_sampler_tone_per_stem` でも、登録・
割り当て・Undo 1回での巻き戻し（音色ごと消える）を確認した
（証拠: `evidence/issue-0101/drive-results.txt`）。

### 2. root_note は決定的に導かれる（空なら 60 を明記） — ✅

単体テスト `root_note_for_picks_the_most_frequent_pitch`（最頻値と
同数時の先勝ち）と `root_note_for_empty_notes_is_default_60` で
固定した。実駆動でも、`other`（ノート [69, 72, 76, 81]、全て
1回ずつ→先勝ちで 69）は root_note 69、ノート空の3ステムは
60 になった。

### 3. 書き出しが無音でなく、抽出メロディの周波数が含まれる — ✅

分解後のプロジェクトを `daw --export-wav` で書き出し、測定した:
ピーク **0.7191**、RMS **0.2603**（無音でない）。Goertzel 法の
周波数別強度は、メロディの4音 A4 440Hz = 0.04398、C5 523.25Hz
= 0.02788、E5 659.26Hz = 0.02325、A5 880Hz = 0.04614 に対し、
対照周波数 D4 293.66Hz = 0.00006、F4 349.23Hz = 0.00022 で、
**約100〜700倍**の差があった。設計の前提どおり、これは
「ステム素材が root_note=69 基準でピッチシフトされて鳴る」音
であり、素材冒頭の A4 が各ノートのシフト先に現れる形で4周波数
すべてが検出された。

### 4. GUI でタイムラインと tones パネルで観測でき、再生できる — ✅

Xvfb（:98）＋lavapipe の実アプリ駆動（`evidence/issue-0101/
drive.sh`、`drive2.sh`）:
- XDND ドロップ→分離完了後、タイムラインに4ステムのトラックと
  クリップが現れ、保存プロジェクトの音色登録・割り当て・ノート列
  を assert した（`shot1-timeline.png`）。
- ウィンドウを縦に広げると **07 TONES パネルに4音色のチップ**
  （melody_only / voca…、/ drum…、/ bass…、/ othe…）が見えた
  （`shot4-tones-panel.png`）。
- 再生中はトランスポート表示が **0.3s・BAR 1 BEAT 1 → 0.5s・
  BAR 1 BEAT 2** と進み、プログレスバーも伸びた
  （`shot5-play-a.png`、`shot6-play-b.png`）。ただしこの
  ソフトウェアレンダリング環境では再生ヘッドの進みが実時間より
  遅かった（1.5秒間に 0.2s 分）。進行そのものは確認できたが、
  実時間性はこの環境では未検証である。
- 実ディスプレイ・実音声デバイスでの確認は未検証。

### 5. MCP／API の状態ダンプでも同じ状態が観測できる — ◐ 部分（MCP は完全確認、API は制約により同形確認のみ）

- **MCP**: `studio-mcp --project-file` で分離済みプロジェクトを
  開き、`get_project` のダンプがプロジェクトファイルと JSON として
  完全一致すること、その中に4音色・tone_id 割り当て・ノート列
  [69, 72, 76, 81]・root_note 69 が含まれることを assert した
  （`evidence/issue-0101/mcp_dump.py`）。
- **API**: `studio-api` はプロジェクトファイルの読み込みを持たず、
  空のプロジェクトから始まる現行アーキテクチャ（状態共有は
  ADR-0010 のとおり GUI↔MCP がファイル経由）のため、分離結果
  そのものを API から読み出す経路は存在しない。その代わり、
  音色登録と割り当てが API のコマンド（`add_tone`／
  `set_track_tone`）と `GET /project` ダンプでも同じ形
  （tones／tone_id／sampler）で観測できることを駆動で示した
  （`evidence/issue-0101/api_dump.py`）。分離結果の正準なダンプは
  プロジェクトファイル自体であり、MCP で完全一致を確認済み。
  **したがって条件5は API 側が未達の部分達成**であり、API に
  プロジェクトファイル読み込みを足す作業はフォローアップ
  **#102** として起票した（レビュー round 1 の指摘を受けて、
  当初 ✅ としていた主張を是正した）。
