### AC3: Rust からの推論手段を確認し、推奨方式と #22 への入力情報を残す — ✅

Rust からの実行経路は **実地で確認した**:
`ort` クレート（ONNX Runtime バインディング、版は 2.0.0-rc.15）+
`load-dynamic` で libonnxruntime（1.32）を読み込み、Rust から MODNet の
推論が成功した（出力 [1,1,512,512]、1回の実行 630ms で Python 実測と一致）。
注意点:
- `ort` は 2.0 系がまだ RC で、API が RC ごとに変わる（本調査でも
  Environment の作り方と ndarray 0.17 要求に当たった）。版を固定すること。
- 既定の「ビルド時に実行バイナリをダウンロードする」経路は、本環境では
  CDN が 403 を返して使えなかった。#22 では `load-dynamic` + 実行時に
  libonnxruntime を同梱する方式を第一候補とし、CI でダウンロード経路が
  通るかは実装時に確認する（代替: tract-onnx は純 Rust だが演算子対応と
  速度にリスクがあり、本命にはしない）。

## 推奨方式（#22 への申し送り）

- **M1 の実装は MODNet を採用する**。理由: 実行できた候補の中で境界品質が
  最良、Apache-2.0 で製品利用に問題なし、26MB と軽く、0.6〜1.0 秒/フレームは
  #22 の「重い処理はオフラインで進捗表示」という設計に合う。
- 入力形式: クリップの素材ファイル（#10 のフレーム展開と同じ経路で
  フレーム PNG 列にする）。処理は 512×512 にリサイズして推論し、
  アルファを元解像度へ戻す。
- 出力形式: フレームごとのアルファマスク列（PNG、フレーム列と同じ
  ディレクトリ規約）＋合成済みプレビュー。適用はコマンド経由
  （クリップに切り抜き指定を持たせ、状態ダンプに現れる形）。
- 将来の高品質モードとして BiRefNet への差し替え余地を残す
  （モデル実行部分を1モジュールに閉じる）。ただし BiRefNet は
  ユーザーの実機（メモリ・GPU）で動くか未検証であり、採用判断は
  実機確認のうえで人間が行うのが望ましい。
- RVM はリアルタイムプレビューで切り抜きが欲しくなった場合の候補。
  現品質では最終出力には使わない。
