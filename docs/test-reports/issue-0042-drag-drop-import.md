## 受け入れ条件ごとの結果

### AC1: WAV をドロップすると、トラック・時刻にそのファイルの長さでクリップが置かれる — ✅（代替規則で）

- `event()` が `WindowEvent::DroppedFile` を受け、`handle_drop`
  が decode_audio で長さを取り、`edit::drop_placement_command`
  （選択中トラック、無効なら先頭、再生ヘッド位置、素材の長さ）
  が組み立てる AddClip を History 経由で適用する。波形・音声
  マップ・保存も通常配置と同じ並びで更新する。
- テスト（イシュー指定名）`drop_position_maps_to_track_and_time`:
  選択優先・フォールバック・配置不能（トラック無し／長さ 0）。
- 実アプリ証拠: トラック2を選択してから XDND でドロップし、
  start_ms 183（ドロップ時点の再生ヘッド）・duration_ms 2000
  （2秒ファイルの実尺）で保存された（`evidence/issue-0042/`）。

### AC2: 対応外のファイルをドロップしても何も起きず、ログに理由が出る — ✅

- 拡張子 .wav のみ許可（`is_supported_drop_path`、大文字小文字
  不問、テスト `drop_accepts_only_wav_paths`）。対応外・デコード
  不能・配置不能・コマンド拒否の各経路が理由付きログを出して
  状態を変えない。
- 実アプリ証拠: notes.txt のドロップで
  `drop rejected: ... (unsupported file type; only .wav)` が出て、
  総クリップ数は変わらなかった。
- 複数ファイルは先頭1件のみ処理し、残りは
  `drop skipped: ...` とログに出す（1秒以内の連続ドロップを
  同じバーストとみなすヒューリスティクス。nannou がファイル
  ごとにイベントを送り、グループ情報がないための措置）。

### AC3: 置かれたクリップが通常のクリップと同じく再生・移動・トリムできる — ✅

- クリップはコアの AddClip が作る通常の Clip で、ドロップ固有の
  状態を持たない。実アプリでドラッグ移動（start 183→421）が
  保存とダンプに反映されることを確認した。再生・トリムは通常
  クリップと同一経路（構造上の担保）。

## レビュー所見への記録（非ブロッキング）

- バースト判定の副作用: 拒否されたドロップでも `last_drop_at`
  が更新されるため、別々の単発ドロップが1秒以内に連続すると
  2件目が誤ってスキップされ得る。実操作ではほぼ起きず、
  代替手段のないヒューリスティクスとして妥当と判断された。
- ドロップ成功時に `dropped_source`（ダブルクリック配置と
  サンプラーの素材）がドロップしたファイルに切り替わる。
  「直近に取り込んだ素材を次の配置素材にする」解釈で一貫して
  おり、害は確認されていない。
