## 確認した事実（証拠付き）

### Vital の配布形態とライセンス

- 作者 Matt Tytel。GPLv3 のオープンソースで、GitHub の公開は公式
ビルドより遅れる。形式は VST/VST3/AU/LV2/CLAP＋スタンドアロン、
Linux 版あり（Ubuntu 18.04 以降、GUI には OpenGL 3 が必要）。
（出典: KVR の製品情報、各レビュー・公式情報の横断確認）
- 本アプリ（rust-studio）のライセンスは MIT（ルート Cargo.toml）。

### プリセット（.vital）の形式 — 実物で確認

- Vital 公式の公開 S3 にある実プリセット（"Wormhole"、622,940
バイト）を取得し、プレーンな JSON としてパースできた。
トップレベルは author / comments / macro1–4 / preset_name /
preset_style / settings / synth_version で、settings は 776
エントリの数値パラメータ辞書。ウェーブテーブルはプリセット内に
埋め込まれるためファイルは大きくなりやすい（KVR での言及とも
一致）。詳細は `evidence/issue-0071/preset-analysis.txt`。
※ファクトリープリセットは再配布不可の別ライセンスのため、
サンプルファイル自体はリポジトリに含めていない。
- エンジン状態 = プリセット JSON であることの裏付け: Vita
（DBraun/Vita、GPLv3）は Vital のシンセエンジンをライブラリ化し、
`to_json()` で状態を.vital として書き出し、`load_json()` /
`load_preset()` で読み戻して `render()` でヘッドレスに音声生成
する。ホスト経由でも、プラグインのステート機構で同じ JSON を
注入できる見込みが高い（実バイナリでの確認は #72 スパイク）。

### Rust 側ホスティング基盤の成熟度

- **CLAP / clack-host**: 「feature-complete」を謳う Rust の CLAP
ホスト／プラグイン用クレート群（prokopyl/clack、MIT/Apache）。
**試作で実証**: clack を clone し、例示プラグイン
（clack-plugin-gain）をビルドして `cargo test -p clack-host
--test loading` を実行、dlopen → ファクトリ → 記述子取得と
300 スレッド同時ロードが成功した（2件通過）。
証拠: `evidence/issue-0071/clack-prototype.txt`。
- **VST3**: 純 Rust のホストは未成熟。`plughost`（VST3/CLAP、
プロセス分離型）は macOS/Windows のみで Linux 非対応のため
本プロジェクトでは現状使えない。C++ SDK からの自前 FFI は
工数が大きい。
- **LV2**: `rust-lv2`（lv2 クレート）は公式に「ホスティングは
非対応で近い将来も予定なし」。lilv の Rust バインディング上の
`livi` は存在するが「work in progress、未十分テスト」。
- **ヘッドレスの前例**: Vita がエンジン単体でのオフライン
レンダリングを実証している（ただしエンジンリンク方式は
GPLv3 の結合になる。本アプリの `render_mix` もオフライン
レンダリングなので、ヘッドレス方式との相性は良い。

### GPLv3 の含意（FSF 公式 FAQ #GPLAndPlugins の整理に基づく）

- fork/exec で呼ぶ別プロセスのプラグインは別プログラム。
動的リンクして関数呼び出しとデータ構造を共有する場合は単一
プログラムを形成し、結合配布では全体に GPL が及ぶというのが
FSF の立場。
- 形態別: インプロセス読み込み＝最もグレー（同梱配布は不可、
実行時結合の解釈が残る）／別プロセス＝別プログラムとして
扱える／エンジン直接リンク＝明確に結合著作物で、本アプリの
GPLv3 化が前提になり MIT 方針と衝突／外部連携＝含意なし。
- どの形態でも、Vital のバイナリやファクトリープリセットを
本アプリが同梱・再配布しないことが前提。

## 方式比較（要約。詳細は ADR-0017）

| 方式 | 可否 | 工数感 | 主なリスク |
|------|------|--------|-----------|
| (a) ホスティング＋GUI 埋め込み | CLAP なら原理的に可。VST3/LV2 は基盤が弱い | 最大 | X11 ウィンドウ埋め込みと OpenGL 文脈、nannou とのハンドル受け渡しが未検証。GPL も最もグレー |
| **(b) ヘッドレス CLAP（別プロセス）** | ロードまで試作で実証。残りは Vital 実バイナリでの検証 | 中 | 公式 Linux 版 CLAP の有無とステート注入の実挙動が未検証（#72 スパイクで最初に潰す） |
| (b') エンジン直接リンク | Vita が実証済み | 中〜大 | 配布形態が GPLv3 前提になり MIT 方針と衝突。C++ ビルド/FFI |
| (c) スタンドアロン外部連携 | 可（仮想 MIDI＋PipeWire/JACK） | 小〜中（ただし DAW に MIDI 出力が要る） | 書き出しに統合できない（実時間キャプチャのみ）。状態がプロジェクトに残らない |

## 推奨と残る判断点

- **推奨: (b) ヘッドレス CLAP ホスティング（別プロセス）＋
プリセット JSON 注入。GUI 編集は #72 の範囲外**（音作りは
スタンドアロン Vital で行い、.vital を参照する）。
- ユーザーに判断いただきたい点:
1. 方式 (b)＋別プロセス＋CLAP を採用するか。
2. #72 でアプリ内 GUI 編集を対象外としてよいか。
3. 前提として、公式 Linux 版 Vital の入手（アカウント経由の
ダウンロード）は利用者側で行う形でよいか（本アプリは
同梱しない）。
- 覆す条件: スパイクで公式 Linux 版に CLAP が無い／ステート
注入でプリセットが再現できない場合は、LV2（livi）への差し替え
か (c) への格下げを再提案する（ADR-0017 に明記）。

## 検証環境の制約

- Vital の Linux バイナリは公式サイトのアカウント経由配布のため
本調査では入手していない。したがって「Vital 実バイナリでの
音声処理・ステート注入・GUI」は未検証で、#72 の前提スパイク
として ADR に明記した。試作で実証したのは clack-host による
CLAP プラグイン一般のロードまで。
