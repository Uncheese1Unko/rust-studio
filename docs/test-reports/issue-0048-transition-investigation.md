- 結論: **ADR-0014**「トランジションは後続クリップの属性として持ち、合成は CPU ブレンド＋既存テクスチャ経路で行う」を**提案として記録**した。合成方式は試作で裏付けた技術選定として調査の結論にするが、モデルの持ち方と尺の意味論は設計判断（ADR-0006）のため、採用の決定は人間に渡した（イシューに `needs-decision` を付与）。本レポートはその状態を正直に記録する。

## 受け入れ条件ごとの結果

### AC1: トランジションの表現方式（モデルの持ち方、長さと種類の置き場所）が ADR として決定され、記録されている — ⚠️ 記録は完了。決定は人間に渡した（needs-decision）

- [ADR-0014](../adr/0014-transition-as-clip-attribute-cpu-blend.md) を作成し、`docs/adr/index.md` に登録した。当初は「採用（決定者：エージェント）」として記録したが、独立レビュー round 1 の指摘（後述）を受け、ADR-0006 とイシューの実装方針（「方式の確定は設計判断として人間に確認する余地を残す」）に従い、ステータスを**提案**に改めた。モデルの持ち方は設計判断であり、AI が確定させない。イシュー #48 に `needs-decision` ラベルと決定依頼コメントを付け、推奨案と選択肢を提示した。
- 推奨案の要点：
  - 後続クリップの属性として持つ。`Clip` に `transition_in_kind`（`none` / `cross_dissolve`）と `transition_in_ms` を追加し、どちらも `#[serde(default)]` で旧形式 JSON と互換にする。音声フェード（`fade_in_ms`、Issue #34）の前例と一貫する。
  - 設定はコマンド層経由（`SetClipTransition` を想定）。検証は種類で分け、`cross_dissolve` のとき「0 < duration_ms <= 当該クリップの長さ」を必須とし、`none` のときは解除として `duration_ms = 0` のみ許可し 0 に正規化する（解除の意味論はレビュー round 1 の指摘3を受けて明記した）。
  - 対象範囲は同一トラックで直接隣接する境界のみ。隣接はプレビュー適用の条件とし、設定自体は隣接を必須にしない（移動・分割のたびの整合管理を避けるため）。
  - 時間窓は後続クリップの先頭 `[start_ms, start_ms + transition_in_ms)`、α は直線。フレームのソース時刻は `offset_ms + (t - start_ms)` で計算する（レビュー round 1 の指摘2を受けて修正。詳細は AC3）。タイムラインの尺は変えない（xfade 方式は不採用）。

### AC2: 2つのフレームを α ブレンドした合成画像が試作で作られ、プレビューの描画経路（nannou のテクスチャ描画）で表示できることが証拠付きで確認されている — ✅

- 試作（使い捨て example、本体には入れず証拠取得後に削除）で、デモ素材と同じ生成条件の2フレーム（testsrc2 と色相 +90 の testsrc2、320×180）を、切り抜き合成（Issue #22 の `composite_pixel`）と同じ式 `out = prev * (1 - α) + next * α` でブレンドした。
  - 入力: [frame-a.png](evidence/issue-0048/frame-a.png)、[frame-b.png](evidence/issue-0048/frame-b.png)
  - 出力: [blend-025.png](evidence/issue-0048/blend-025.png)（α=0.25）、[blend-050.png](evidence/issue-0048/blend-050.png)（α=0.5）、[blend-075.png](evidence/issue-0048/blend-075.png)（α=0.75）
  - 数値確認（試作の標準出力 [proto-stdout.txt](evidence/issue-0048/proto-stdout.txt)）: 画素 (8,8) で A=(60,0,0)、B=(0,36,0) に対し、α=0.25 → (45,9,0)、α=0.5 → (30,18,0)、α=0.75 → (15,27,0) と、式どおりの値になった。
- 表示確認: α=0.5 の合成画像を、プレビューと同じ経路（`wgpu::Texture::from_path` で読み、`draw.texture` で描画）で表示する試作アプリを Xvfb＋lavapipe で実行した。テクスチャ読み込みは成功し、スクリーンショット [proto-window.png](evidence/issue-0048/proto-window.png) で合成画像が表示されていることを確認した（採取した複数点の画素が合成画像と一致。一部の輪郭上の点のみ GPU の線形補間の差異があった）。

### AC3: 実装 PBI の受け入れ条件に使える形で、対象範囲と検証方法が決まっている — ✅（ADR-0014 の採用が前提）

後続の実装 PBI（#49）は、ADR-0014 が採用されれば、その前提で次の形に受け入れ条件を書ける。

- 対象範囲: 同一トラックで直接隣接するクリップ境界のみ。種類はクロスディゾルブのみ。時間窓は後続クリップの先頭、α は直線。尺・配置は不変。
- 検証方法（#49 で使える形）:
  - コア: `SetClipTransition` の検証（`cross_dissolve` で長さ 0 以下・クリップ長超過の拒否、失敗時に状態不変）と、状態ダンプ（JSON）に `transition_in_kind` / `transition_in_ms` が観測できることの単体テスト。**解除のケース**（付けてから `kind = none` で外すと、ダンプが `none` / 0 に戻ること）も含める。
  - 純粋関数: 時刻から α と前後フレームのソース時刻を求める関数の単体テスト（窓の開始・中間・終了、隣接でない場合にトランジションが効かないこと）。ソース時刻は `offset_ms + (t - start_ms)` で、**offset ≠ 0 のケース（分割で生じたクリップ対。前クリップ・後続クリップの両方）を必ず含める**。
  - 画面: 隣接2クリップのプロジェクトで、窓の中間時刻のプレビューが α≈0.5 の合成になっていることをスクリーンショット＋画素照合で確認する（本調査の試作と同じ照合方法が使える）。解除後は合成されていないことも確認する。状態ダンプでも同じトランジション設定が観測できること。
  - MCP: `SetClipTransition` が MCP 経由でも適用・解除でき、ダンプで観測できること。

## 調査の過程で分かったこと

- プレビューのフレーム列は素材（source）単位で全フレームが展開されている（`FrameStore` は source 文字列がキー）。そのため前クリップの「タイムライン終了後」のフレームも、ソースの続きとしてフレーム列の中に存在する（末尾クランプも既存）。
- ただしソース時刻の計算には注意が要る。現行の `media.rs::source_time_ms` は `offset_ms`（Issue #32）を加えておらず、タイムライン経過時間をそのまま使っている。分割で生じたクリップ（offset ≠ 0）ではこれはソース時刻として誤りであり、#49 では ADR-0014 の定義（`offset_ms + (t - start_ms)`）に合わせて計算する必要がある。既存実装の式を仕様として固定してはいけない（レビュー round 1 の指摘2）。
- 現行の `draw.texture` 経路にはテクスチャ単位の α 指定がなく、2テクスチャの重ね描きで済ませるには追加の仕組みが要る。CPU 合成は切り抜き（#22）の前例どおりで、320×180・10fps ではコストも問題にならない。
