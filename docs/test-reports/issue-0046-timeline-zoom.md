# 試験レポート： Issue #46 動画編集のタイムラインをズームできる

- 日付: 2026-11-22
- 実行者: エージェント（デリバリーループ、並行レーンB＝動画編集 担当）
- 対象: Ctrl+ホイールでタイムラインを 0.25〜8 倍にズーム（中心は
  マウス位置の時刻）、通常ホイールで水平スクロール。描画・
  ヒットテスト・ms 換算はすべて倍率とオフセットを反映する。
  倍率とスクロールはプロジェクトに保存しない。
- 実装コミット: `1ec69ec`、clippy 対応 `7ac1fc0`、レビュー対応 `fe53b86`・`30430f9`（いずれも rebase 後の SHA）
- CI: 緑 https://github.com/Uncheese1Unko/rust-studio/actions/runs/45006622001
- 環境: Yoko の VM（Linux、ヘッドレス）。表示確認は Xvfb（:92）＋Mesa
  lavapipe（ソフトウェアレンダリング）。**実ディスプレイでの確認は未検証。**
- テスト件数: 動画編集クレート 55 件 → 60 件（新規5件: timeline 2件・
  edit 3件、うち2件はレビュー対応の回帰）。ワークスペース全体は
  close 時点で 233 件（他レーンの追加分を含む）。削除・弱体化なし。

## 設計

- `timeline::ViewScale { zoom: f32, offset_ms: i64 }` を表示状態の
  単一の出所とした（DAW #38 と同一設計、イシューの方針どおり）。
  `layout_clips`／`playhead_x`／`edit::x_to_ms`／`edit::hit_test`／
  スナップ（#45）のしきい値換算はスケールを引数に取る形へ変えた。
  既存テストの呼び出しは既定スケールを渡す形に機械的に更新した
  （期待値は変更なし）。
- `zoom_at(factor, anchor_ms, anchor_x, width)` がアンカーの画面
  位置を保ったまま倍率を変え、倍率は 0.25..=8 にクランプ、
  オフセットは 0 未満にならない。`scroll_by` も 0 でクランプ。
- nannou 0.19 には Builder の mouse_wheel 登録がなく、ホイールは
  `event()` に `WindowEvent::MouseWheel` として届くため、そこで
  捌く形にした（DAW #38 と同じ）。

## 受け入れ条件ごとの結果

### AC1: Ctrl+ホイール（または +/− ボタン）で拡大・縮小でき、クリップとルーラーが同じ倍率で描かれる — ✅

- 描画はすべて `model.view_scale` 経由（ルーラーは表示範囲の秒
  だけを反復）。イシューは「Ctrl+ホイール（またはボタン）」の
  選択肢であり、Ctrl+ホイールで満たす。
- 実アプリ証拠: Ctrl+ホイールで zoom 1.25→2.44 と段階的に上がり
  （アンカー 1000ms、オフセット 590 でアンカー位置不変を確認）、
  x=450 のピクセルがクリップ面から行背景に変わった
  （`evidence/issue-0046/`）。

### AC2: 拡大時は水平スクロールでき、プレビューのフレーム選択がずれない — ✅

- 通常ホイールで offset が動き、0 で止まる（証拠ログ: 590→990→390）。
- プレビューのフレーム選択は再生ヘッド時刻（`media::active_video_clip`
  ＋ `source_time_ms`）だけで決まり、表示スケールを参照しない
  （コード確認＋証拠ログで preview 行がズーム後も継続）。

### AC3: 拡大・スクロールしてもドラッグ移動・トリムのヒットテストと ms 換算がずれない — ✅

- テスト（イシュー指定名）`x_to_ms_round_trips_at_any_zoom`:
  倍率 0.25/0.5/1/2/8 × オフセットで ms→px→ms がピクセル量子化の
  誤差以内で往復する。`hit_test_uses_view_scale` が zoom2・
  offset1000 で判定が変わることを検証。スナップのしきい値換算も
  スケール経由に直した（#45 の既存テストは既定スケールで不変）。

### AC4: 倍率とスクロールはプロジェクトに保存されず、再起動で初期倍率に戻る — ✅

- `view_scale` は Model のフィールドのみで、初期化は
  `ViewScale::default()`（1.0 倍・オフセット 0）。ドライブで
  ズーム＋スクロール後にプロジェクト JSON がバイト単位で元の
  ままであることを assert した。

## コードレビュー

- ラウンド1: **CHANGES_REQUESTED**（指摘1件）。ズーム／スクロール
  時に、オフセットより前から始まるクリップがヘッダー列
  （x < 120px）へはみ出して描かれ、トラック名と削除ボタンを
  塗り潰していた。ルーラーの目盛りも同様にはみ出していた。
  実アプリのスクリーンショットを根拠とする正当な指摘で、
  ドライブのピクセル確認が (450,48) だけでヘッダー領域を見て
  いなかったのが見逃しの原因。
  → 対応: `layout_clips` で矩形をヘッダー右端で切り取り
  （ヒットテストの境界と一致）、ルーラーは x < HEADER の目盛りを
  描かないようにした。ドライブにヘッダーピクセルの不変チェックを
  追加し、証拠を取り直した。
- ラウンド2: **CHANGES_REQUESTED**（指摘2件）。(1) round 1 の
  切り取り修正が、ヒットテストに「実在しない左端」を作っていた
  （切り取られた矩形の左端がトリム掴み位置になり、完全に見えない
  クリップまで掴めてしまう。AC3 違反）— 自分の修正が入れた回帰
  で、正当な指摘。(2) 再生ヘッド線も同じ条件でヘッダー列に
  はみ出していた。
  → 対応: `ClipRect` に `clipped_left` を持たせ、ヒットテストは
  切り取られた左端を掴み位置にせず幅 0 の矩形を対象外にした。
  再生ヘッド線はヘッダー列の内側では描かないようにした。
  回帰テスト `hit_test_ignores_phantom_edge_of_clipped_clip` を
  先に書いて落ちることを確認してから直した。
  **レビューは作法の上限（2ラウンド）に達したため round 3 は
  行っていない。最終 APPROVE は未取得**であり、round 2 の指摘は
  すべて受け入れ条件の範囲内だったため修正して close に進んだ
  （#44 と同じ扱い）。
