イシュー本文の候補1・2を実施した。設計の小判断（実装担当の判断として記録）: 候補1は横スクロールではなく折り返し（複数行化）を採用。候補2は「チップの右クリックで削除」「チップのダブルクリックで改名」を採用した（イシューが挙げた候補のうち、既存の操作流儀—トラック改名のダブルクリック、履歴経由で Undo 可能—と揃うもの）。

## 実装内容

- **候補1（横溢れ）**: `apps/daw/src/tones.rs` のレイアウトをフロー配置化した。`flow_layout` がチップ→作成→削除を単一走査で配置し、右端（`limit_x` = ウィンドウ幅 − 16）を超えるアイテムは次の行の左端へ折り返す。行頭のアイテムは幅が残り幅を超えてもその行に置く（置き場が無いための仕様として明記）。`panel_height(tones, limit_x)` は行数に応じて伸びる。描画とヒット判定は同じ `flow_layout` 経由で一致する。
- **候補2（GUI 操作）**:
  - 右クリック削除: チップを右クリックすると、割り当て中かどうかを問わずその音色を `Command::RemoveTone` で削除する（履歴経由、Undo 可）。後処理は既存の DELETE ボタンと同じ（保存＋`refresh_audio_map`）。
  - 改名: チップのダブルクリックで `ToneRenameSession`（トラック改名と同じ意味論。Enter で `Command::RenameTone`、Esc で中止）に入る。編集中はチップに編集中文字列＋キャレットを表示する。他の編集セッション（トラック改名・BPM）とは排他で、`update`／`mouse_wheel`／Esc のガードと外部再読込での打ち切りにも `tone_rename` を含めた。ダブルクリックの2回目は割り当てトグルを発火しない（1回目は通常クリックとしてトグルが1回発火する。ポーリング型判定では避けがたい挙動としてレビューで記録された）。

## 実アプリ駆動（GUI 証拠）

Xvfb（display :97）＋ lavapipe ソフトウェアレンダリングで実アプリを駆動した。**実ディスプレイ／実 GPU での見え方は未検証。**

駆動スクリプトは `evidence/issue-0076/drive.sh`、標準出力ログは `gui-stdout.txt`、スクリーンショットは `01-wrapped.png`／`02-after-ops.png`。音色20件のプロジェクトで確認した:

- 折り返し: 1行目・2行目の両方にチップ面が描かれ（ピクセル確認）、右端 x=950 にはチップが無い（はみ出しなし）。
- 右クリック削除: 2行目先頭の未割り当て音色を右クリックし、音色数が 20 → 19 になった（ダンプ JSON で確認）。
- 改名: チップをダブルクリックして `tone rename begin: tone 10`、Z を入力して Enter で `after tone rename:` が出て、名前が "Tone 01Z" になった。

- 駆動の知見: xdotool の `click` は押下が短くフレームポーリングに拾われないことがあるため、押下を 0.4 秒保持する方式にした。実施中、VM のパッケージ消失（xdotool 等）が再発し、復旧を待って再実行した回がある（コード側の問題ではない）。
