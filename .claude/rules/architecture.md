# Architecture — 構造のルール

判断の根拠は `docs/adr/`（特に 0002〜0005）。ここは実施ルールの要約。

## コマンド層（単一の変更経路）

- プロジェクト状態（タイムライン、トラック、クリップ、各種パラメータ）の変更は、
  `crates/studio-core` の**コマンド経由でのみ**行う。GUI のイベントハンドラ、
  HTTP API、MCP サーバーはすべて同じコマンドを実行する。状態を直接書き換える
  コードをアプリ側に書かない。
- コマンドは検証してから適用する。失敗するコマンドは状態を変えない。
- コマンドはシリアライズ可能にする（API／MCP から JSON で受けられる形）。
  将来の undo/redo と操作ログは、このコマンド列の上に作る。

## クレート構成

- `crates/studio-core`：モデル＋コマンド層。GUI・メディア・ネットワークに
  依存しない。単体で `cargo test` が完結する。
- `crates/studio-scripts`：Lua 実行基盤とスクリプトカタログ（ADR-0020）。
  video-editor と studio-mcp が共有し、スクリプト一覧の形を経路で
  ずらさない。プロジェクト状態は持たない（変更はコアのコマンド層のみ）。
- `apps/video-editor` / `apps/daw`：nannou の GUI、メディア入出力、再生。
  モデルとコマンドはコアに委ね、アプリは「表示と入出力」に徹する。
- MCP サーバーと HTTP API はコアのコマンド層の薄いラッパーにする。
  ビジネスロジックをラッパー側に書かない。

## AI ネイティブ／computer use テスト可能性

- HTTP API はプロジェクト状態の全量ダンプ（JSON）を返す。画面で起きたことが
  API でも観測できることが、自動テストの前提。
- UI 要素には安定した識別子（名前）を持たせる。computer use エージェントが
  画面操作で辿れるようにする。
- 乱数・現在時刻に依存する振る舞いは、テストで固定できるよう注入可能にする。

## メディア処理

- デコード／エンコード／再生の重い処理はコアに入れない。アプリ側の
  メディア層に閉じ、コアは「素材への参照とパラメータ」だけを持つ。
