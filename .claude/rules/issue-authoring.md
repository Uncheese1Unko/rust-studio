# Issue Authoring — EPIC + PBI

作業を GitHub イシューとして起票するときのルール（ohta-rh 氏のハーネスに倣う）。

## 1. 構造

- 計画された作業はすべて **EPIC イシュー＋子 PBI イシュー**。EPIC に属さない
  単独イシューは作らない。合う EPIC がなければ先に EPIC を作る。
- **EPIC** = ユーザーが名前を付けられる成果1つ。ゴール、スコープ境界、
  着手順付きの子一覧を持つ。実装タスク自体は持たない。
- **PBI** = それ単体で観測できる価値を届け、独立に実装・検証・マージできる
  振る舞いの縦スライス。レイヤーで割らない（「バックエンド部分」は PBI ではない）。
- 子は GitHub の sub-issue として EPIC にリンクし、EPIC のチェックリストと同期する。
- ラベル：EPIC に `epic`、子に `pbi`。タイトル：`[EPIC] <成果>` /
  `<ユーザーができるようになること、または起きなくなること>`。
- 依存する PBI は本文に `blocked by #N` を書く。EPIC の一覧は上から取れる順に並べる。
- まだ誰も動かしていない前提（新しいライブラリ、nannou のビルド、外部ツール）は
  設計フェーズの**調査 PBI** にする。受け入れ条件は「前提が証拠付きで確認できたこと」。

## 2. 根本原因が起票の前提

**根本原因を1文で言えるまで、イシューを作らない。**

- 不具合：実入力で再現し、原因まで追う。再現手順と証拠（file:line、ログ、失敗した
  クエリ）を記録する。「たぶん X」は仮説であって根本原因ではない。
- 機能・改善：根本原因は背後の問題 — 誰が、何に阻まれていて、なぜ現状で賄えないか。
  解法を言い換えたもの（「ボタンが必要」）は根本原因ではない。
- 原因が確定しなければ、受け入れ条件を「証拠付きで根本原因が特定できたこと」とする
  調査 PBI を作る。推測の上に実装 PBI を作らない。
- 複数の症状に1つの原因なら1 PBI。1つの症状に複数の原因なら複数の PBI。

## 3. 手戻りゼロ・チェックリスト（`gh issue create` の前に全て満たす）

- [ ] `git fetch` 後の `origin/main` に対して調査した（古いチェックアウトでない）
- [ ] 根本原因が証拠付きで1文になっている
- [ ] 受け入れ条件が観測可能で、それぞれ確認方法（コマンド or 具体的手順）がある
- [ ] スコープ内／外の両方が書いてある。途中で見つけた隣の問題は別 PBI にした
- [ ] 触るファイル／モジュールが書いてあり、既存の類似コードを検索して参照した
- [ ] 本文に未決事項が残っていない。実装者が判断すること（データ形状、公開
      インターフェース名、エラー時の振る舞い）は決めて書いてある。人間の設計判断が
      要るものは起票前に聞く（イシューの中に先送りしない）
- [ ] 依存関係と順序が明示されている
- [ ] 実装者が、そのイシューだけで（起票に至る会話なしに）着手できる
- [ ] 1回の変更で収まる大きさ。でなければ割る
- [ ] 本文の末尾に「完了の定義」（`.claude/rules/definition-of-done.md` の項目を
      そのままチェックボックスで）がある

## 4. テンプレート

`.github/ISSUE_TEMPLATE/epic.md` と `.github/ISSUE_TEMPLATE/pbi.md` を使う。
